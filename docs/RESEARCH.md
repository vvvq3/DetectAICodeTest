# Выжимка исследования «Как отличить C#-код, написанный человеком, от кода Claude Code»

Источник — PDF-исследование (23 стр.), проведённое ранее. Здесь — всё, что влияет на алгоритм.

## Главные выводы
- На уровне коммита в 10 строк отличить нельзя; надёжность растёт с объёмом. Текстовый детектор надёжен с ~2–3 тыс. символов (60–100 строк C#), ниже 700 символов — заметно хуже. Единица анализа — чанк добавленного кода, MR = несколько чанков + процессные сигналы.
- Ни один признак сам по себе не доказывает ИИ (многие — просто хорошие практики senior). Различающая сила — из **плотности и единообразия признака по всему диффу**, **сочетания признаков** и **сдвига относительно истории автора / нормы проекта**.
- Стилевые признаки легко маскируются инструкцией («пиши как в проекте», CLAUDE.md). **Устойчивы к мимикрии**: признаки корректности (токены отмены, структурное логирование), форма изменения (связный многослойный дифф, тесты в том же коммите), скорость, структурный «отпечаток» модели.
- Детектор должен опираться на **несколько независимых групп сигналов**, чтобы для обхода надо было победить все одновременно.
- Ложные срабатывания концентрируются на шаблонном коде и коротких фрагментах (DTO, контроллеры, конфигурации EF Core, DI-регистрации) — понижать их вес.
- Исключать: `*.Designer.cs`, `*.g.cs`, `Migrations/`, `*.resx`, lock-файлы, явный шаблонный код, чанки < 700 символов.
- Риск ложного обвинения: результат — оценка с объяснением, не доказательство; калибровать порог на низкую долю ложных срабатываний на заведомо ручном коде. Риск «выглядеть как ИИ» у сеньоров с чистым стилем, команд со строгими анализаторами (StyleCop/Roslyn analyzers), авторов с английскими комментариями.

## Признаки кода Claude Code в C# (таблица исследования)
| Группа | Признак | Пример | Сила | Убирается инструкцией? |
|---|---|---|---|---|
| Документация | XML-doc на каждом публичном члене, шаблонные формулировки | `/// <summary>Gets or sets the order identifier.</summary>`, полностью заполненные `<param>`, `<returns>` | средняя (зависит от норм, StyleCop SA1600) | да, легко |
| Комментарии | Пошаговое «повествование», пересказ кода | `// Validate the request`, `// Map entity to DTO`, `// Step 1:` | высокая, если есть | да |
| Комментарии | Безупречный английский; нет TODO, HACK, ссылок на тикеты, закомментированного кода | команда пишет по-русски, а новый файл — грамотный английский | средняя | частично |
| Именование | Длинные описательные имена без сокращений | `cancellationToken` вместо `ct`, `existingCustomer`, `normalizedEmail`, `result`, `response` | средняя | частично |
| Синтаксис | Равномерное использование новейших возможностей языка | file-scoped namespace, primary constructors, collection expressions `[]`, `required`, `record` для DTO, `is not null`, switch-выражения | низкая сама по себе, высокая как скачок относительно истории | да |
| Защитный код | Guard-клаузы везде, даже при nullable | `ArgumentNullException.ThrowIfNull(request);`, `ThrowIfNullOrWhiteSpace` | средняя | частично |
| Async | Сквозная передача токена отмены, суффикс Async | `CancellationToken cancellationToken = default` по всей цепочке, `ConfigureAwait(false)` в библиотеках | средняя | **нет — это корректность** |
| Логирование | Шаблоны структурного логирования | `_logger.LogWarning("Order {OrderId} not found", orderId)` вместо `$"..."` | средняя | **нет** |
| Структура | «Полная» архитектура на маленькую задачу | интерфейс + реализация + `AddXxx(this IServiceCollection)` + options-класс + валидатор | средняя | частично |
| Классы | Модификаторы «по умолчанию» | `sealed` у всех классов, `private readonly` у всех полей, `static` у чистых методов | низкая–средняя | да |
| Исключения | Сообщения — полные предложения с точкой и `nameof` | `throw new InvalidOperationException($"Order {orderId} cannot be cancelled because it has already shipped.");` | средняя | частично |
| Тесты | Тесты в том же коммите; много граничных случаев | `// Arrange / Act / Assert`, имена `Method_Scenario_ExpectedResult`, `[Theory]`+`[InlineData]`, `test@example.com` | высокая (в сочетании) | частично |
| Форма диффа | Связное изменение многих слоёв за раз | контроллер + сервис + репозиторий + DI + тесты + миграция в одном MR без последующих «fix typo» | высокая | **нет** |
| Побочные артефакты | Markdown-документация и эмодзи | новые `docs/*.md` с разделами Overview/Usage, `CLAUDE.md`, ✅ в выводе | высокая, если есть | да |
| Масштаб | Рефакторинг соседнего кода «заодно» | небольшая фича меняет 15 файлов, переименовывает и упрощает смежные методы | средняя | частично |

Контраст: типичный вывод агента — XML-doc с `<param>`/`<returns>`, `GetOrderByIdAsync(Guid orderId, CancellationToken cancellationToken = default)`, `AsNoTracking()`, `FirstOrDefaultAsync(..., cancellationToken)`, `if (order is null) { _logger.LogWarning("Order {OrderId} was not found", orderId); return null; }`.
Типичный ручной: `GetOrder(Guid id)`, `var o = await _db.Orders.Include(x => x.Items).FirstOrDefaultAsync(x => x.Id == id); if (o == null) throw new NotFoundException($"order {id} not found"); // TODO: в middleware`, `_mapper.Map<OrderDto>(o)`.

## Прямые артефакты Claude Code (почти доказательство, но легко убираются)
- Трейлер `Co-Authored-By: Claude <noreply@anthropic.com>` (иногда с названием модели); строка «Generated with Claude Code» в описании PR/MR. Отключается настройкой `attribution`, но при коммите через Bash иногда остаётся.
- Ссылка `https://claude.ai/code/session_...` в коммите и описании (облачные сессии).
- Файлы `CLAUDE.md`, `.claude/settings.json`, `.claude/commands/`, упоминание `.claude` в `.gitignore`.
- Описание MR в формате `## Summary` / `## Test plan` с ровными маркированными списками.
- Наличие — сильный сигнал «да», отсутствие — ничего не говорит (ghost-author и т.п. вычищают).

## Сигналы ритма и формы работы (процесс)
| Сигнал | Что считать | Где взять |
|---|---|---|
| Скорость производства | значимые строки на час активной работы между соседними пушами | время пуша (сервер), время коммитов |
| «Готовность с первого раза» | сколько правок получает новый файл позже | история файлов |
| Связность диффа | сколько слоёв затрагивает одно изменение | дифф MR |
| Тесты вместе с кодом | тесты в том же коммите; отношение строк тестов к строкам кода | дифф |
| Реакция на ревью | время от комментария до исправления, ширина исправления | discussions/notes |
| Сообщения коммитов | единообразный Conventional Commits, императив, тело со списком изменений | git log |
| Документация как побочный продукт | новые .md, README-разделы, комментарии-объяснения в конфигурации | дифф |
| Период полураспада кода | доля строк, переписанных в следующие 30–90 дней | git blame |

## Стартовый набор признаков на Roslyn (по чанку, нормировка на строки/конструкции + сдвиг относительно нормы репозитория)
- **Комментарии**: плотность `//`; доля публичных членов с XML-doc; доля «пересказывающих» комментариев (слова совпадают с идентификаторами следующей строки); язык комментариев; число TODO/HACK и ссылок на тикеты; закомментированный код.
- **Именование**: средняя длина локальных имён и параметров; доля имён ≤ 3 символов; доля общих имён (`result`, `response`, `data`, `item`).
- **Синтаксис**: file-scoped namespace, primary constructors, collection expressions, `record`, `required`, `is not null` против `!= null`, switch-выражения, target-typed `new()`, доля `var`.
- **Защитный код**: guard-клаузы на публичный метод; `ThrowIfNull` и аналоги; проверки null при nullable.
- **Async**: доля async-методов с `CancellationToken`; доля вызовов, куда токен передан; суффикс Async; `ConfigureAwait(false)`.
- **Логирование и исключения**: шаблоны `ILogger` против интерполяции; сообщения исключений — предложения с точкой; плотность try/catch.
- **Структура**: распределение длины методов; цикломатическая сложность; доля `sealed` и `readonly`; единообразие порядка членов.
- **Тесты**: комментарии Arrange/Act/Assert; шаблон имён тестов; доля `[Theory]`; тестовые данные вроде `example.com`.
- **Форма диффа (MR)**: число затронутых слоёв; тесты в том же коммите; доля новых файлов; новые `.md`; строки на час между пушами.

## Архитектура (рекомендация исследования)
GitLab API → предобработка (без сгенерированных файлов, Roslyn, чанки 2–3 тыс. символов) → 4 независимые группы: стилометрия (AST-признаки), нейросеть (не в прототипе), переписывание (запрещено заказчиком — внешний API), процесс/артефакты → калибровка и объединение → (агрегация за период — не в прототипе) → отчёт с объяснением, какие группы сигналов дали вклад.

## Мимикрия — что остаётся при обходе
| Обход | Ломает | Остаётся |
|---|---|---|
| CLAUDE.md со стилем проекта | комментарии, XML-doc, именование, модификаторы | корректность (токены, логирование), форма диффа, скорость, структурный отпечаток |
| «Пиши как этот автор» | поверхностный стиль | объём и скорость, связность многослойного диффа, тесты в том же коммите |
| Чистка метаданных | трейлеры, футеры, ссылки | всё содержательное |
| Ручная доработка 20–50% | часть текстовых признаков | форма диффа, скорость, отпечаток в непереписанных частях |
| Гигиена коммитов | скорость, «готовность с первого раза» | текст кода, связность, отпечаток |

Устойчивое: признаки корректности; сдвиг относительно нормы (у нас — нормы проекта, т.к. даты не используем); сам `CLAUDE.md` в репозитории.

## Критерии готовности (цели пилота из исследования)
Чанк: ROC AUC ≥ 0.90 в домене клиента; ложные срабатывания на ручном коде ≤ 3%; полнота в режиме «стиль проекта» ≥ 0.6. Справедливость: разброс FPR между группами авторов не более 2 раз.
