## Резюме

Отличить код Claude Code от ручного на уровне отдельного коммита в 10 строк нельзя, а на уровне месяца работы — можно. При 50+ чанках кода и точности детектора 90–95% на чанк доля ИИ-кода оценивается с погрешностью порядка ±7–10 п.п. Условие — калибровка на C#-коде, близком к коду клиента, и опора не только на стиль, который агент легко маскирует.

- **Рынок.** Есть классификаторы по тексту кода (Span: 95% на чанках 2–3 тыс. символов, поддерживает C#; Codespy, Copyleaks) и точная атрибуция через телеметрию (Claude Code Analytics, OpenTelemetry, Git AI). Заявленным цифрам вендоров без открытой методики доверять нельзя.
- **Наука.** В знакомом домене детекторы дают 90%+, при смене домена кода — падают почти до случайного уровня. Зато у каждой модели устойчивый «отпечаток», поэтому задача «Claude или нет» решается лучше универсальной.
- **Мимикрия.** Инструкция «пиши как в проекте» убирает комментарии, XML-doc и именование. Не убирает форму работы агента (связный многослойный дифф, тесты в том же коммите, скорость сверх личной нормы), признаки корректности и структурный отпечаток.
- **Объём.** Единица анализа — чанк от 2–3 тыс. символов (около 60–100 строк C#), единица отчёта — месяц. Систематическое смещение отдельного автора не усредняется — нужна его личная базовая линия.
- **Риски.** Оценка эффективности сотрудников — высокорисковая категория EU AI Act (обязанности со 2 декабря 2027), в Молдове с 23 августа 2026 действует GDPR-подобный закон № 195/2024. Результат — оценка с интервалом, не доказательство.

**Рекомендация: гибрид.** Там, где разработчики готовы включить телеметрию, она даёт точную долю и эталон для обучения. Там, где нет, — ансамбль из стилометрии на Roslyn, процессных признаков из GitLab и теста переписыванием через Claude с поправкой на ошибки за период.

## Постановка задачи и рамки

Задача — для каждого разработчика за период (месяц, несколько десятков MR) оценить долю кода, написанного с помощью Claude Code, с высокой точностью на уровне агрегата. Ошибка на отдельном коммите в 10 строк допустима.

Рамки исследования:
- **Язык:** C# / .NET (ASP.NET Core, EF Core, xUnit/NUnit, типичный enterprise-код).
- **Инструмент ИИ:** Claude Code — агентный CLI, который сам читает репозиторий, правит файлы, запускает сборку и тесты, может делать коммиты. Под ним работают модели Claude (Sonnet, Opus), и их стиль меняется от версии к версии.
- **Противодействие:** разработчик может попросить агента писать «как в проекте» или «как я раньше», в том числе через постоянный файл инструкций CLAUDE.md.
- **Результат:** не бинарный вердикт, а оценка доли ИИ-кода с доверительным интервалом и объяснением, на каких признаках она основана.

Уровни участия ИИ сильно различаются по заметности, поэтому их надо разделять в отчёте:

| Уровень | Как выглядит | Заметность в коде |
|---|---|---|
| 0. Вручную | Человек пишет сам, IDE даёт только классические подсказки (IntelliSense, рефакторинги Rider/ReSharper) | — |
| 1. Строчное автодополнение | Короткие подсказки на 1–5 строк, человек принимает и правит | Низкая: фрагменты мелкие и растворяются в ручном коде |
| 2. Чат + копирование | Человек просит фрагмент в чате и вставляет его | Средняя: целые методы в «чужом» стиле |
| 3. Агент (Claude Code) | Агент сам создаёт и правит файлы, тесты, иногда коммиты | Высокая: крупные однородные блоки, характерные паттерны и процесс |
| 4. Агент + плотная ручная доработка | Агент пишет черновик, человек переписывает существенную часть | Средняя: смешанные сигналы |

Два класса входных данных: содержимое изменений (сам дифф кода) и процесс (история Git, тайминг, MR, ревью). Третий, самый надёжный, — телеметрия инструмента, если компания готова её собирать; она же нужна как эталон для обучения.

## Существующие продукты

Рынок разделился на два подхода. Инструментирование: агент сам сообщает, какие строки он написал, — точно, но требует установки у разработчика. Классификаторы по тексту кода работают ретроактивно по любому репозиторию, но дают вероятность. Для продукта ценны оба: первый как эталон для обучения, второй как основной продукт.

### Классификаторы по тексту кода

| Продукт | Подход | C# | Заявленная точность | Комментарий |
|---|---|---|---|---|
| Span (span-detect-1) | ML-классификатор по чанкам 2–3 тыс. символов, ответ «ИИ / человек / воздержался» | Да | 95% при 5% воздержаний, ~45 тыс. сбалансированных примеров | Деградирует на чанках короче 700 символов; привязывает долю ИИ к разработчику, команде, инструменту |
| Codespy | Синтаксические паттерны + статистика, обучен на 12 моделях, включая Claude Code | Да | 98% (не подтверждено независимо) | Плагин VS Code, GitHub App |
| Copyleaks CodeLeaks | Токенизация по синтаксису языка, устойчивость к переименованию | Да (40+ языков) | 99%+ (самооценка) | Ориентирован на образование и плагиат |
| GPTZero | Перплексия и «burstiness», перенесённые с текста | Нет в списке | ~92% | Перплексия для кода слабее, чем для прозы |
| Exceeds AI | Анализ диффов коммитов и PR | Не указано | Не раскрыта | Позиционируется как аналитика AI-вклада по разработчикам — ближайший конкурент |

Важное предупреждение из того же обзора: исследователи Span проверили конкурента, заявлявшего 98%, и он оказался на уровне случайного угадывания. Цифрам вендоров без открытой методики доверять нельзя.

По пресс-релизу Span модель оценивает именно долю ИИ-кода во фрагменте по латентным признакам: закономерностям в последовательностях токенов, синтаксическим особенностям и стилистической регулярности. Это ровно та постановка, что нужна продукту.

### Инструментирование и телеметрия (точная атрибуция)

| Источник | Что даёт | Ограничения |
|---|---|---|
| Claude Code Analytics (Team/Enterprise) | Строки и PR «с Claude Code» по каждому пользователю; PR получают метку `claude-code-assisted` | Только организации на claude.ai, только GitHub; не работает при Zero Data Retention |
| Claude Code Analytics Admin API | Ежедневно по пользователю: добавлено/удалено строк, коммиты и PR от Claude Code, принятые/отклонённые правки Edit/Write | Агрегаты, без привязки к конкретным строкам |
| OpenTelemetry Claude Code | Метрики `lines_of_code.count`, `commit.count`, `pull_request.count`, события по каждому вызову инструмента | Нужно включать на машине разработчика или через managed settings |
| Git AI (open source) | Построчная атрибуция в Git Notes: какой агент и модель написали строку; сохраняется при rebase/squash | Нужна установка у каждого разработчика |
| GitHub Copilot Usage Metrics API | Предложено/принято строк по пользователю, включая режим агента | Только Copilot |

Метод атрибуции Claude Code Analytics полезно скопировать для разметки обучающих данных. Строки PR нормализуются (обрезка пробелов, нижний регистр, унификация кавычек) и сопоставляются с выводом сессий Claude Code, которые правили те же файлы в окне от 21 дня до мержа до 2 дней после. Строки, переписанные разработчиком более чем на 20%, не засчитываются ИИ; считаются только «значимые» строки длиннее 3 символов.

Git AI принципиально отказывается «угадывать»: его авторы считают ретроактивную детекцию антипаттерном, потому что агенты могут сами точно сообщать о своих строках. Для продукта это аргумент в пользу гибридной схемы: где телеметрия есть — использовать её, где нет — классификатор.

### Платформы engineering analytics

Jellyfish, LinearB, Swarmia и DX в основном работают с метаданными (время цикла PR, количество коммитов) и опросами разработчиков. По оценкам конкурентов из Exceeds AI, они не отделяют ИИ-код от человеческого на уровне строк. Отзыв предвзятый, но совпадает с их публичным позиционированием. Ниша «доля ИИ по разработчику на основе анализа кода» пока занята слабо: Span, Exceeds AI и инструменты самих вендоров.

## Научные методы детекции

В лабораторных условиях детекторы дают 90%+, но при смене домена кода точность падает до уровня случайного угадывания. Главный вывод: универсальный детектор «из коробки» не сработает, нужна калибровка на C#-коде, близком к коду клиента, и опора на модель-специфичные отпечатки Claude.

| Семейство методов | Идея | Результаты | Применимость к Claude + C# |
|---|---|---|---|
| Вероятностные zero-shot: DetectGPT, DetectCodeGPT, Binoculars | ИИ-текст лежит в зоне высокой вероятности модели; проверка через возмущения или сравнение двух моделей | DetectCodeGPT: +7,6% AUC к прошлому SOTA за счёт возмущения пробелами и переносами строк. Binoculars: >90% на тексте при 0,01% ложных срабатываний, но на коде авторы не проверяли | Слабо: весов Claude нет, придётся брать открытую модель-заместитель. В коде много «низкоэнтропийных» токенов, сигнал слабее |
| Переписывание: Ye et al., AAAI 2025 | Просим LLM переписать код; свой код модель меняет мало, человеческий — сильно | Значимый прирост AUROC к SOTA zero-shot; работает через закрытые API | Сильно: у нас есть API того же семейства моделей. Можно переписывать фрагмент самим Claude и мерить сходство |
| Обученные классификаторы (CodeBERT/GPTSniffer, UniXcoder, ModernBERT) | Энкодер дообучается на размеченных парах | На AICD Bench средний Macro F1 0,63 в знакомом домене и языке, 0,42 на незнакомом языке, ~0,20 на незнакомом домене | Средне: нужны свои данные C# + Claude; без них — переобучение |
| Стилометрия и классические признаки (TF-IDF n-граммы, AST) | Интерпретируемые признаки стиля и структуры | На том же бенчмарке TF-IDF + SVM обобщается на новые языки лучше нейросетей; ИИ чаще использует «говорящие» имена вроде `result`, `output`, а человек — короткие `li`, `nums`, `cur` | Сильно как часть ансамбля: объяснимо и устойчиво |
| Атрибуция конкретной модели: CodeT5-Authorship, LLM-NodeJS | Многоклассовая классификация «какая LLM написала» | 97,56% при различении GPT-4.1 и GPT-4o на C; 95,4% среди пяти LLM; на JS атрибуция держится после минификации (91%) и переименования (93%) | Сильно: у каждой модели структурный «отпечаток», задача «Claude или нет» проще универсальной |
| Водяные знаки: SWEET | Генератор встраивает статистическую метку в высокоэнтропийные токены | Работает лучше post-hoc методов, но только если метку встроил вендор | Неприменимо: публично документированного водяного знака в коде Claude нет |
| LLM как судья (zero-shot промпт) | Спросить модель «человек или ИИ» | Gemini с цепочкой рассуждений — Macro F1 ~0,62 на бинарной задаче AICD | Слабо как самостоятельный метод |

Четыре вывода из бенчмарков, которые прямо влияют на дизайн:
- **Доминирующий источник ошибок — сдвиг домена, а не языка.** Детектор, обученный на олимпиадных задачах, бесполезен на enterprise-коде ASP.NET. C# в AICD Bench присутствует только как незнакомый язык в тестовой выборке.
- **Гибридный код** (человек + LLM) детекторы чаще всего относят к чистому ИИ, а код, специально сгенерированный «под человека», путают в обе стороны.
- **Ложные срабатывания концентрируются на шаблонном коде и коротких фрагментах.** В C# это DTO, контроллеры, конфигурации EF Core, DI-регистрации — их нужно исключать или понижать в весе.
- **Отпечатки конкретной модели устойчивы** к переименованию и удалению комментариев. Это основание сфокусироваться на одном семействе (Claude), а не строить универсальный детектор.

## Признаки кода Claude Code в C#

Ни один признак сам по себе не доказывает ИИ: многие из них — просто хорошие практики, которым следует сильный senior. Различающая сила появляется из трёх вещей: плотности и единообразия признака по всему диффу, его сочетания с другими признаками и резкого сдвига относительно собственной истории автора.

Список ниже — гипотезы, составленные по наблюдаемым тенденциям моделей Claude и публичным наблюдениям разработчиков (vibecheck, обсуждения сообщества). Силу каждого признака нужно измерить на размеченных данных: стиль меняется от версии модели к версии.

| Группа | Признак | Пример в C# | Сила | Убирается инструкцией? |
|---|---|---|---|---|
| Документация | XML-doc на каждом публичном члене, шаблонные формулировки | `/// <summary>Gets or sets the order identifier.</summary>`, полностью заполненные `<param>`, `<returns>` | Средняя (зависит от норм проекта, StyleCop SA1600) | Да, легко |
| Комментарии | Пошаговое «повествование» и пересказ кода | `// Validate the request`, `// Map entity to DTO`, `// Step 1:` | Высокая, если есть | Да, легко |
| Комментарии | Безупречный английский; отсутствие TODO, HACK, ссылок на тикеты, закомментированного кода | Команда пишет по-русски, а в новом файле — грамотный английский | Средняя | Частично |
| Именование | Длинные описательные имена без сокращений | `cancellationToken` вместо `ct`, `existingCustomer`, `normalizedEmail`, `result`, `response` | Средняя | Частично |
| Синтаксис | Равномерное использование новейших возможностей языка | file-scoped namespace, primary constructors, collection expressions `[]`, `required`, `record` для DTO, `is not null`, switch-выражения | Низкая сама по себе, высокая как скачок относительно истории автора | Да («пиши как в проекте») |
| Защитный код | Guard-клаузы везде, даже при включённых nullable reference types | `ArgumentNullException.ThrowIfNull(request);`, `ThrowIfNullOrWhiteSpace` в начале каждого метода | Средняя | Частично |
| Async | Сквозная передача токена отмены и суффикс Async | `CancellationToken cancellationToken = default` во всей цепочке вызовов, `ConfigureAwait(false)` в библиотеках | Средняя | Нет — это не стиль, а корректность |
| Логирование | Правильные шаблоны структурного логирования | `_logger.LogWarning("Order {OrderId} not found", orderId)` вместо интерполяции `$"..."` | Средняя | Нет |
| Структура | Аккуратная «полная» архитектура на маленькую задачу | Интерфейс + реализация + `AddXxx(this IServiceCollection)` + options-класс + валидатор | Средняя | Частично |
| Классы | Модификаторы «по умолчанию» | `sealed` у всех классов, `private readonly` у всех полей, `static` у чистых методов | Низкая–средняя | Да |
| Исключения | Сообщения — полные предложения с точкой и `nameof` | `throw new InvalidOperationException($"Order {orderId} cannot be cancelled because it has already shipped.");` | Средняя | Частично |
| Тесты | Тесты в том же коммите, что и код; много граничных случаев | `// Arrange / Act / Assert`, имена `Method_Scenario_ExpectedResult`, `[Theory]` + `[InlineData]`, данные `test@example.com` | Высокая (в сочетании) | Частично |
| Форма диффа | Связное изменение многих слоёв за раз | Контроллер + сервис + репозиторий + DI + тесты + миграция в одном MR без последующих «fix typo» | Высокая | Нет |
| Побочные артефакты | Markdown-документация и эмодзи | Новые `docs/*.md` с разделами Overview и Usage, `CLAUDE.md`, ✅ в выводе консоли или тестов | Высокая, если есть | Да |
| Масштаб | Рефакторинг соседнего кода «заодно» | Небольшая фича меняет 15 файлов, переименовывает и упрощает смежные методы | Средняя | Частично |

Самые устойчивые к мимикрии — признаки корректности и формы изменения: токены отмены, структурное логирование, связный многослойный дифф, тесты в том же коммите. Модель не ухудшает корректность по просьбе «пиши как раньше», а форму работы агента стилевая инструкция не меняет вообще.

Контраст на одном методе. Типичный вывод агента:

```csharp
/// <summary>
/// Retrieves an order by its identifier.
/// </summary>
/// <param name="orderId">The unique identifier of the order.</param>
/// <param name="cancellationToken">A token to cancel the operation.</param>
/// <returns>The order if found; otherwise, <c>null</c>.</returns>
public async Task<OrderDto?> GetOrderByIdAsync(Guid orderId, CancellationToken cancellationToken = default)
{
    var order = await _dbContext.Orders
        .AsNoTracking()
        .Include(o => o.Items)
        .FirstOrDefaultAsync(o => o.Id == orderId, cancellationToken);

    if (order is null)
    {
        _logger.LogWarning("Order {OrderId} was not found", orderId);
        return null;
    }

    return order.ToDto();
}
```

Типичный «ручной» код в живом проекте:

```csharp
public async Task<OrderDto> GetOrder(Guid id)
{
    var o = await _db.Orders.Include(x => x.Items).FirstOrDefaultAsync(x => x.Id == id);
    if (o == null) throw new NotFoundException($"order {id} not found"); // TODO: в middleware
    return _mapper.Map<OrderDto>(o);
}
```

Второй вариант может написать и агент по инструкции, а первый — аккуратный человек. Поэтому классификатор должен смотреть не на один метод, а на распределение таких признаков по всем MR автора за период и сравнивать его с прошлым периодом того же автора.

## Процессные и мета-сигналы из Git и MR

Процессные сигналы почти не зависят от стиля кода, поэтому инструкция «пиши как я» их не маскирует. Это главный противовес мимикрии. Подделать их можно, но это требует ручной гигиены коммитов, то есть усилий, которые сами по себе снижают выгоду от обмана.

### Прямые артефакты Claude Code

- По умолчанию Claude Code добавляет в коммиты трейлер `Co-Authored-By: Claude <noreply@anthropic.com>` (иногда с названием модели), а в описание PR — строку «Generated with Claude Code» (claudelog). Это отключается настройкой `attribution` (с версии 2.0.62 она заменила `includeCoAuthoredBy`). Но в issue-трекере есть сообщения, что при коммите через Bash-инструмент трейлер иногда появляется и при выключенной настройке.
- Облачные сессии добавляют ссылку вида `https://claude.ai/code/session_…` в коммит и описание PR, и отдельной настройки для неё, по этому issue, нет.
- Файлы `CLAUDE.md`, `.claude/settings.json`, `.claude/commands/` в репозитории, а также упоминание их в `.gitignore`.
- Описание MR в формате `## Summary` / `## Test plan` с ровными маркированными списками.

Эти артефакты — почти стопроцентное доказательство, но их легко убрать. Существуют готовые инструменты вроде ghost-author, которые вычищают трейлеры, футеры PR и конфиги агентов перед пушем. Поэтому их наличие — сильный сигнал «да», а отсутствие ничего не говорит.

### Сигналы ритма и формы работы

| Сигнал | Что считать | Где взять | Подделываемость |
|---|---|---|---|
| Скорость производства | Значимые строки на час активной работы между соседними пушами; сравнение с личной нормой автора | Время пуша с сервера GitLab (не время коммита — его задаёт клиент) | Средняя: можно дробить и задерживать пуши |
| «Готовность с первого раза» | Сколько правок получает новый файл в следующие 2 недели; человек обычно наращивает файл серией мелких коммитов | История файлов | Средняя |
| Связность диффа | Сколько слоёв затрагивает одно изменение: контроллер, сервис, DI, тесты, миграция | Дифф MR | Низкая |
| Тесты вместе с кодом | Доля MR, где тесты появились в том же коммите, что и реализация; отношение строк тестов к строкам кода | Дифф | Низкая |
| Реакция на ревью | Время от комментария ревьюера до исправления и ширина исправления | API MR (discussions, notes) | Средняя |
| Сообщения коммитов | Единообразный Conventional Commits, императив, тело со списком изменений | git log | Высокая: легко переписать |
| Документация как побочный продукт | Новые `.md`-файлы, README-разделы, комментарии-объяснения в конфигурации | Дифф | Высокая |
| Период полураспада кода | Какая доля добавленных строк переписана в следующие 30–90 дней | git blame по времени | Не подделывается, но запаздывает |

Для продукта важна деталь: вы работаете с MR, то есть, вероятно, с GitLab. Встроенные contribution metrics Claude Code пока поддерживают только GitHub Cloud и GitHub Enterprise Server. Для GitLab-клиентов эталонную разметку придётся собирать через Analytics Admin API (агрегаты по пользователю за день), OpenTelemetry или Git AI.

## Минимальный объём кода и агрегация

Текстовый детектор надёжен начиная с фрагмента примерно в 2–3 тыс. символов; ниже 700 символов точность заметно падает (Span, по обзору fast.io). Поэтому единица анализа — не коммит, а чанк добавленного кода, а единица отчёта — период. При 50+ чанках за месяц доля ИИ-кода оценивается с погрешностью порядка ±7–10 п.п., если точность на чанк 90–95% и откалибрована на домене клиента.

| Единица | Объём | Что реально достижимо |
|---|---|---|
| Коммит на 10–30 строк | 300–1 000 символов | Ниже порога надёжности по тексту; работают только прямые артефакты (трейлер, ссылка на сессию) |
| Чанк | 2–3 тыс. символов, около 60–100 строк C# (оценка) | 95% при 5% воздержаний у Span на их данных; на новом домене без калибровки — заметно ниже |
| MR | 200–1 500 строк | Несколько чанков + процессные сигналы → вероятность «MR в основном от агента» |
| Месяц | Десятки MR, порядка 30–150 чанков (оценка) | Доля ИИ-кода с доверительным интервалом — основная единица отчёта |

Просто посчитать долю «ИИ»-меток нельзя: ошибки классификатора смещают оценку. Если известны чувствительность s (доля ИИ-чанков, которые детектор ловит) и специфичность t (доля человеческих, которые он не трогает), долю восстанавливают поправкой Рогана–Гладена. Здесь q̂ — доля чанков с меткой «ИИ», n — число чанков:

```
p̂ = (q̂ − (1 − t)) / (s + t − 1)
SE(p̂) = sqrt( [ p·s(1−s) + (1−p)·t(1−t) ] / n ) / (s + t − 1)
```

График исследования (модельный расчёт: ошибки чанков независимы, s = t, 95%-интервал): при 50 чанках погрешность доли ИИ составляет ±18,5 п.п. при точности 80% на чанк, ±10,4 п.п. при 90% и ±6,7 п.п. при 95%. Цель — ±10 п.п. Погрешность падает как 1/√n; при s = t она не зависит от истинной доли ИИ.

Три оговорки важнее формулы:
- s и t должны быть измерены на коде того же клиента, на выборке с эталонной разметкой из телеметрии. Цифры вендора или бенчмарка для этого не годятся.
- Систематическая ошибка не усредняется. Если естественный стиль автора похож на Claude, все его чанки сдвинуты в одну сторону, и 300 чанков дадут уверенный неверный ответ. Против этого работают личная базовая линия автора и процессные сигналы.
- Вместо жёстких меток лучше усреднять откалиброванные вероятности: при хорошей калибровке это несмещённая оценка с меньшим разбросом.

Из анализа исключаются сгенерированные файлы (`*.Designer.cs`, `*.g.cs`, `Migrations/`, `*.resx`, lock-файлы), явный шаблонный код и чанки короче 700 символов.

## Мимикрия стиля и обход детекции

Стилевую инструкцию («пиши как в проекте», «как я раньше») агент выполняет хорошо, поэтому стилевые признаки из раздела выше маскируются за минуты. Не маскируются форма работы агента, признаки корректности и структурный «отпечаток» модели. Детектор должен опираться на несколько независимых групп сигналов, чтобы для обхода пришлось победить все одновременно.

Инструменты обхода уже существуют в готовом виде. Например, навык humanize-code для C# запрещает агенту пошаговые комментарии, XML-doc, повторяющие имя члена, бессмысленные try/catch и TODO-заглушки. ghost-author вычищает трейлеры, футеры PR и конфиги агентов перед пушем.

| Способ обхода | Что ломает | Что остаётся | Цена для разработчика |
|---|---|---|---|
| CLAUDE.md со стилем проекта | Комментарии, XML-doc, именование, модификаторы | Корректность (токены отмены, логирование), форма диффа, скорость, структурный отпечаток | Почти нулевая |
| «Пиши как этот автор» + примеры его кода | Поверхностный стиль конкретного человека | Объём и скорость сверх личной нормы, связность многослойного диффа, тесты в том же коммите | Низкая |
| Чистка метаданных (`attribution`, ghost-author) | Трейлеры, футеры, ссылки на сессии | Всё содержательное | Низкая |
| Ручная доработка 20–50% строк | Часть текстовых признаков; гибрид детекторы часто относят к ИИ | Форма диффа, скорость, отпечаток в непереписанных частях | Средняя |
| Гигиена коммитов (дробление, задержка пушей) | Сигналы скорости и «готовности с первого раза» | Текст кода, связность изменений, отпечаток | Средняя–высокая |
| Полное переписывание вручную | Практически всё | Ничего | Высокая — по сути человек пишет сам |

Из исследований: перефразирование обходит zero-shot детекторы текста более чем в 90% случаев (Schneider et al.). Код, сгенерированный моделью, специально дообученной под «человеческий» стиль, детекторы путают в обе стороны (AICD Bench). При этом дообученные классификаторы держатся лучше: на CodeMirage CodeT5+ сохраняет F1 выше 80% на незнакомых генераторах и перефразированном коде (по данным авторов AICD Bench).

Что остаётся устойчивым и на чём строить защиту:
1. **Сдвиг относительно личной базовой линии.** Стиль человека довольно стабилен годами. Если в этом месяце у автора одновременно выросли объём, связность диффов и плотность тестов, а распределение признаков сместилось, это видно даже при идеальной маскировке поверхностного стиля.
2. **Признаки корректности.** Просьба «пиши как раньше» обычно не заставляет модель забыть токен отмены или перейти на интерполяцию в логах.
3. **Тест переписыванием через Claude.** Даже замаскированный код Claude сохраняет глубинные решения модели: декомпозицию, порядок шагов, выбор API. При переписывании тем же семейством он меняется меньше, чем человеческий. Это гипотеза — её надо проверить на красной команде.
4. **Сам CLAUDE.md.** Если в репозитории лежит инструкция «пиши без XML-doc и с сокращёнными именами, как человек», это прямое свидетельство.

Практическая граница: если разработчик переписал большую часть строк, код стал его. Anthropic в собственной атрибуции использует похожее правило: строки, изменённые более чем на 20%, не засчитываются Claude Code. Для продукта разумно принять то же определение.

Обязательный элемент прототипа — набор «красной команды»: Claude Code решает реальные задачи в репозиториях, похожих на клиентские, в пяти режимах. По умолчанию; с CLAUDE.md в стиле проекта; с имитацией конкретного автора; с навыком «очеловечивания»; с ручной правкой 20% строк. Полнота детектора измеряется отдельно по каждому режиму.

## Риски, этика и юридические аспекты

Главный риск — ложное обвинение конкретного человека: ошибка детектора ложится на оценку его работы. Поэтому результат должен подаваться как оценка с интервалом, а не как доказательство, и никогда не быть единственным основанием для кадрового решения. Ниже — фактическая картина, а не юридическая консультация; для запуска нужен юрист.

### Регулирование

| Норма | Что важно | Срок |
|---|---|---|
| EU AI Act, Annex III п. 4 | Системы, которые оценивают работу или мониторят поведение работников, относятся к высокому риску (Ogletree). Оценка эффективности программистов по коду почти наверняка сюда попадает при продаже клиентам в ЕС | После Digital Omnibus (Регламент 2026/1744) обязанности применяются со 2 декабря 2027 (Cuatrecasas, Mondaq) |
| AI Act, ст. 26 | Заказчик-работодатель обязан информировать работников и их представителей об использовании такой системы (LearnSignal) | Вместе с правилами высокого риска |
| Закон Молдовы № 195/2024 | Аналог GDPR: код, привязанный к автору, — его персональные данные. Нужны правовое основание, прозрачность, вероятно — оценка воздействия (DPIA) для систематического мониторинга сотрудников | В силе с 23 августа 2026; штрафы вводятся поэтапно: 10%, 40%, затем 100% расчётной суммы по годам (ecom.md) |

Содержание обязанностей для высокорисковых систем включает управление рисками, техническую документацию, прозрачность и человеческий надзор (actuia). Детектор ИИ-кода как часть оценки эффективности наследует эти требования, поэтому методику, метрики точности и проверку на смещения лучше документировать с первого дня.

### Принципы продукта

- **Формулировка.** Показывать «долю кода, созданного с помощью ИИ», а не «нечестность». Использование Claude Code обычно разрешено или поощряется работодателем; ценность метрики — честно нормировать продуктивность и сравнивать качество ИИ- и ручного кода.
- **Асимметрия ошибок.** Калибровать порог на низкую долю ложных срабатываний на заведомо ручном коде (цель — единицы процентов), даже ценой пропусков.
- **Только агрегат.** Менеджеру — доля за период с интервалом и пометкой «недостаточно данных», если чанков мало. Пометки по отдельным коммитам — только самому разработчику.
- **Объяснимость и оспаривание.** В отчёте — какие группы сигналов дали вклад. Разработчик видит свой отчёт и может его оспорить.
- **Проверка на смещения.** Измерить ложные срабатывания отдельно для сеньоров с чистым стилем, команд со строгими анализаторами (StyleCop, Roslyn analyzers), авторов с английскими комментариями. Именно они рискуют выглядеть «как ИИ».
- **Дрейф моделей.** Новые версии Claude меняют стиль; качество детектора нужно отслеживать ежемесячно на эталонной выборке и переобучать.
- **Закон Гудхарта.** Если за ИИ наказывают — его прячут, и детекция превращается в гонку вооружений. Если использование нейтрально или поощряется — разработчики сами включают телеметрию, и детектор нужен только там, где её нет.
- **Код клиента.** Тест переписыванием отправляет код во внешний API. Это нужно согласовать с условиями обработки данных провайдера и договорами клиентов; альтернатива — локальная модель-заместитель.

## Архитектура и план прототипа

Рекомендуется ансамбль из четырёх независимых групп сигналов с единой калибровкой и агрегацией за период. Самая ценная и самая трудоёмкая часть — не модель, а эталонные данные на C# с достоверной разметкой.

```
Источник: GitLab API — MR, коммиты, диффы, push-события, обсуждения ревью
  → Предобработка — без сгенерированных файлов, разбор Roslyn, чанки по 2–3 тыс. символов
  → 4 группы: Стилометрия (AST-признаки Roslyn, градиентный бустинг) | Нейросеть (UniXcoder, ModernBERT, дообучение на C#)
              | Переписывание (Claude переписывает, мерим сходство) | Процесс, артефакты (ритм, форма MR, ревью, трейлеры, CLAUDE.md)
  → Эталонная разметка (телеметрия, Git AI, красная команда) обучает и калибрует модели
  → Калибровка и объединение — стекинг, изотоническая калибровка, вероятность на чанк и на MR
  → Агрегация за период — поправка Рогана–Гладена и базовая линия автора
  → Отчёт — доля ИИ-кода ± интервал по разработчику и команде
```

Текстовые детекторы работают по чанкам, процессный — по MR; эталонная разметка нужна и для обучения, и для измерения s и t в поправке за период.

### Стартовый набор признаков на Roslyn

Признаки считаются по чанку и нормируются на строки или на число конструкций. Для каждого также хранится сдвиг относительно базовой линии автора и нормы репозитория.

| Группа | Признаки |
|---|---|
| Комментарии | Плотность `//` на строку; доля публичных членов с XML-doc; доля «пересказывающих» комментариев (слова комментария совпадают с идентификаторами следующей строки); язык комментариев; число TODO/HACK и ссылок на тикеты; закомментированный код |
| Именование | Средняя длина локальных имён и параметров; доля имён ≤ 3 символов; доля общих имён (`result`, `response`, `data`, `item`) |
| Синтаксис | file-scoped namespace, primary constructors, collection expressions, `record`, `required`, `is not null` против `!= null`, switch-выражения, target-typed `new()`, доля `var` |
| Защитный код | Guard-клаузы на публичный метод; `ThrowIfNull` и аналоги; проверки null при включённых nullable reference types |
| Async | Доля async-методов с `CancellationToken`; доля вызовов, куда токен передан; суффикс Async; `ConfigureAwait(false)` |
| Логирование и исключения | Шаблоны `ILogger` против интерполяции; сообщения исключений — предложения с точкой; плотность try/catch |
| Структура | Распределение длины методов; цикломатическая сложность; доля `sealed` и `readonly`; единообразие порядка членов |
| Тесты | Комментарии Arrange/Act/Assert; шаблон имён тестов; доля `[Theory]`; тестовые данные вроде `example.com` |
| Форма диффа (уровень MR) | Число затронутых слоёв; тесты в том же коммите; доля новых файлов; новые `.md`; строки на час между пушами |

### План прототипа

1. **Эталонные данные.**
   a. Заведомо ручной C#-код: история ваших и клиентских репозиториев до появления агентов (например, до 2023 года) и C#-часть набора The Heap из AICD Bench.
   b. Парный корпус Claude: берём закрытые MR, откатываем репозиторий на родительский коммит и даём Claude Code ту же задачу. Получаем два решения одной задачи — человеческое и агентское — во всех пяти режимах красной команды.
   c. Живая разметка: 3–5 добровольцев с Git AI или OpenTelemetry на месяц.
2. **Базовый детектор признаков:** консольное приложение на C# и Roslyn, которое выгружает добавленный код по MR, режет на чанки по границам методов и классов и считает признаки в CSV. Сверху — бустинг (ML.NET или LightGBM) и анализ важности признаков.
3. **Процессные признаки** по GitLab API на уровне MR и правила для прямых артефактов.
4. **Тест переписыванием через Claude API** на подвыборке: измерить прирост к пунктам 2–3 и стоимость на чанк.
5. **Нейросетевой классификатор** (дообучение UniXcoder или ModernBERT) — только если пунктов 2–4 не хватает.
6. **Агрегация за месяц и базовая линия автора.** Проверка на «синтетических месяцах»: смешиваем известные доли ИИ- и ручных чанков и смотрим, накрывает ли 95%-интервал истину в 95% случаев.
7. **Пилот** на 1–2 командах, где телеметрия служит эталоном.

### Критерии готовности

| Уровень | Метрика | Цель для пилота |
|---|---|---|
| Чанк | ROC AUC в домене клиента | ≥ 0,90 |
| Чанк | Ложные срабатывания на заведомо ручном коде при рабочем пороге | ≤ 3% |
| Чанк | Полнота отдельно по каждому режиму красной команды | Измерить; не ниже 0,6 в режиме «стиль проекта» |
| Месяц | Средняя абсолютная ошибка доли ИИ | ≤ 10 п.п. |
| Месяц | Покрытие 95%-интервала | 90–97% |
| Справедливость | Разброс ложных срабатываний между группами авторов | Не более чем в 2 раза между группами |

Целевые значения — предложения для старта; их стоит уточнить после первых замеров на эталонных данных.
